# Disposable and temporary hosted rehearsals

The default rehearsal uses temporary CI databases and requires no standing staging resource. A separately authorized, time-limited hosted mode reuses the same workload against an isolated Vercel deployment and synthetic-only Supabase project. Registration and provisioning are explicit; an empty hosted registry disables that mode. `.github/workflows/staging-rehearsal.yml` runs the complete rehearsal on pull requests affecting its listed paths, manually, and monthly. It uses PostgreSQL 17 with pinned Supabase CLI 2.45.5, real local Auth/PostgREST, and a production-mode Next server. Existing migration CI separately covers PostgreSQL 15 and 17.

## Execution and safety

The workflow installs locked dependencies and loads `supabase/baseline/pre001_clean_database.sql` plus numbered migrations 001–023 into a fresh disposable stack. The baseline contains schema definitions, not production warehouse rows or private history. `scripts/lib/disposable-baseline.bash` shares the existing migration-test bootstrap. The recovery step first creates its own synthetic league, applies the reviewed `supabase/operations/league_runtime_cutover.sql`, and performs a logical dump/restore into a second disposable database. The workload then seeds two independent synthetic leagues, reapplies the rerunnable cutover, and deletes its fixtures after testing. `supabase stop --no-backup` always destroys the stack and its volumes.

In CI mode all application, Auth and database URLs must be explicit loopback origins. Hosted mode requires the separate registry and preflight described below. Production project references, production application aliases, unknown origins, credentials in HTTP URLs, and URL query overrides are denied. Before application mutation commands, real Auth users finalize signed application sessions and `/api/health/readiness` must attest `environment=local`, `supabaseProjectRef=local`, and the exact checked-out commit. The fixture helper checks actual database columns before inserts and verifies synthetic account identities before cleanup.

The workflow needs no production, Vercel, Supabase management, email, payment or AI credentials. Local API keys come only from `supabase status`. Neither the workload nor its fixtures request Sleeper data or paid AI services. Fixture leagues use unpriced pick assets and synthetic rookie prospect IDs, and all read endpoints access the local runtime directly.

## Workload and assertions

Default workload: a maximum of 10 simultaneous HTTP requests, 120 seconds of paced authenticated reads, and four sequential mutation cycles. Each cycle races two different draft selections for one slot, replays the winning request concurrently, verifies exactly one persisted pick, checks that another roster cannot see the pending selection, then undoes the pick. In the second league, it concurrently repeats offer creation, races acceptance of two offers sharing an asset, replays the winner, and checks both offer status and authoritative ownership in PostgreSQL.

Reads cover runtime, draft state, and each user's inbox across both leagues while mutations run. Assertions reject cross-league state and stale league headers. Two request slots are reserved for mutation races; other workers issue paced reads. The script fails on an unexpected response or failed invariant, then attempts fixture cleanup.

Hard bounds: concurrency 3–25, read duration 10–180 seconds, at most 6,000 HTTP requests, 1–10 mutation cycles, 15-second request timeouts, 2 MiB response bodies, and a duration-plus-120-second overall HTTP deadline. The CI job itself is capped at 30 minutes including container setup, build and recovery. Expected conflict responses (409) are successful race outcomes, not application errors. Default read/command p95 threshold is 2,500 ms; any unexpected error aborts the run. Output contains aggregate timings/counts and commit identity, never cookies, tokens or fixture data.

Manual dispatch accepts concurrency and duration; script validation remains authoritative. Relevant optional environment variables are `LOAD_CONCURRENCY`, `LOAD_DURATION_SECONDS`, `LOAD_MUTATION_CYCLES`, `LOAD_MAX_REQUESTS`, and `LOAD_P95_MS`. Run the safety regressions without Docker using `node --test tests/staging-load.test.mjs`. Full integration requires Docker in the disposable CI job; it has not been substituted with mocked SQL or authentication.

## Temporary hosted mode

Use a dedicated temporary Vercel project and a fresh, synthetic-only Supabase project. A production-backup recovery clone is not a load target. Keep Deployment Protection enabled and use the exact immutable deployment origin, never a production or mutable branch alias. Match the deployed revision, region and function settings deliberately; record any differences from production when interpreting results. No new standing staging resource is required.

Before running, an operator must:

1. Provision the isolated database with the reviewed schema and operational cutover. Complete and remove any bootstrap fixture. The hosted runner refuses preexisting Auth users, memberships, profiles, runtime rows, trades or draft state. It checks cutover privileges and takes a session advisory lease to prevent concurrent test runs. It does not perform global DDL or run the cutover script in hosted mode.
2. Deploy the reviewed commit with staging identity, temporary database credentials, new session/audit keys, no production secrets and no AI/email/payment/feed credentials. Existing application guards disable paid AI, email alerts and machine/admin jobs in staging. Only synthetic runtime, draft and pick-only trade paths are exercised; no Sleeper requests are needed.
3. Register the target in `config/deployment-targets.json` under `stagingTargets`: `name`, `purpose: "synthetic-load"`, `projectRef`, `vercelProjectId`, `deploymentId`, `commitSha`, exact `appOrigins`, exact `databaseHosts`, and ISO `createdAt`/`expiresAt`. The window cannot exceed four hours. Keep real production and protected Supabase references in the shared denylist. Registering a target after deployment does not require rebuilding the application; this operational entry is consumed by the runner.
4. Supply private environment values: `STAGING_TARGET`, `STAGING_PROJECT_REF`, `STAGING_APP_URL`, `STAGING_SUPABASE_URL`, `STAGING_DATABASE_URL`, `STAGING_COMMIT_SHA`, `STAGING_VERCEL_PROJECT_ID`, `STAGING_DEPLOYMENT_ID`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY`. Set `STAGING_LOCAL=0`. The PostgreSQL connection must use direct or session-pooler port 5432, verified TLS, and the registered project identity. `STAGING_DATABASE_CA_FILE` optionally supplies the trusted CA; certificate verification is never disabled.
5. Supply an origin-scoped temporary protection token via `STAGING_PROTECTION_TOKEN`. The default `STAGING_PROTECTION_MODE=oidc` uses `x-vercel-trusted-oidc-idp-token`. A narrowly scoped, revocable temporary share credential can use `STAGING_PROTECTION_MODE=share` and the standard bypass header when OIDC is unavailable. Tokens stay in memory and request headers; no query-string bypass or redirect following is allowed. Do not turn off protection or use a broad permanent token.
6. Set `STAGING_STOP_FILE` to an absolute path in an external task directory, initially absent, and run `node scripts/load-staging.mjs`. Creating that file or sending SIGINT/SIGTERM aborts active requests and triggers cleanup. The watcher checks every 250 ms, including between requests. Independently retain the ability to delete the exact temporary deployment if the runner process is forcibly killed.

All six synthetic users complete real Auth sign-in and application finalization. Signed readiness must match staging environment, exact Supabase reference, Vercel project, deployment ID and commit. This is checked again before each ramp stage. Only then are writes enabled for the two generated fixture league IDs.

Hosted stages are fixed: 3 concurrent requests for 30 seconds, then 10 for 60 seconds, then 25 for 90 seconds. They run one, one and two draft/trade mutation cycles respectively. A stage must pass the privacy/ownership/idempotency assertions, record no unexpected responses, and keep read/command p95 at or below 2,500 ms before the next stage begins. Two request slots are reserved for races; remaining workers issue paced reads.

Hard hosted limits: 4,000 application requests total, 25 request starts per rolling second globally, 25 concurrent requests, 180 measured seconds, 300-second workload deadline, 15-second request timeout, 2 MiB per response, and 64 MiB cumulative response bytes. CI tuning variables do not enlarge these hosted limits. Setup and cleanup use bounded database queries and Auth calls separately. Client cancellation stops dispatch but cannot guarantee that an already-running server function stops immediately.

Cleanup first disables writes on the exact generated runtime rows, removes the exact synthetic data/accounts and releases the lease. Expiry stops new work but does not prevent verified fixture deletion. If cleanup fails or the process is forcibly terminated, treat the target as dirty and destroy it; do not run another workload on it. After results are collected, revoke the temporary protection credential and delete both temporary resources and their registry entry. The target's expiry stops this runner; it is not an automatic provider resource-deletion mechanism.

Use a temporary-project budget as an additional safeguard, without changing a team-wide budget that could affect production. [Vercel Spend Management](https://vercel.com/docs/spend-management) checks every few minutes and its pause action affects production deployments only; it is not an instantaneous dollar cap for a preview test. [Supabase compute](https://supabase.com/docs/guides/platform/manage-your-usage/compute) is billed in whole-hour increments, excluded from its spend cap, and stops accruing compute charges after deletion. Record actual provider usage afterward; the workload limits are not a guaranteed total-dollar ceiling. [Vercel Trusted Sources](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/trusted-sources) documents short-lived OIDC access and precise identity scoping.

Run both safety suites with `node --test tests/staging-load.test.mjs tests/staging-hosted-load.test.mjs`. Unit tests cover target identities, expiry, restored-data refusal, privilege readiness, rate/byte limits, protected-header scope and stop behavior; actual hosted results require a provisioned authorized target.

## Protected hosted workflow

Provision through the protected `temporary-resource-watchdog.yml` workflow with `cost_approved=true`: approval precedes creation, and the same process immediately watches and enforces the temporary target's deadline. Do not create an unattended target. `scripts/hosting/hosted-load.mjs` then handles `HOSTED_LOAD_OPERATION=setup|run|cleanup` through `production-drills.yml`, using `DRILL_TARGET_MANIFEST` with public target metadata and the existing protected `SUPABASE_ACCESS_TOKEN`. Both workflows require reviewed main in `ntricarichi22/Fantasyfootball`. The token is unavailable during dependency installation and is never passed to the load child. See `PRODUCTION_OPERATIONS_DRILLS.md` for the watchdog runbook and cleanup limits.

Provision is fixed to the approved organization `peotkumhnipghqkrtjfs`, project name `cfc-load-drill-20261115`, `us-east-1`, and Micro compute. It lists projects first and refuses duplicate names. The current [create-project API](https://supabase.com/docs/reference/api/v1-create-a-project) requires `organization_slug`; the wrapper obtains it from read-only metadata matching the approved organization, uses a random in-memory database password, and never blindly retries a timed-out creation. Output includes only the proven project's public manifest. The four-hour deadline starts at the provider's actual creation timestamp. A verified startup/quarantine failure triggers exact-target deletion; an unresolvable creation outcome requires metadata inspection before retrying.

As soon as the project is healthy, public signup, phone/anonymous access, configured OAuth/SAML providers and optional hooks/notification channels are disabled. Password sign-in remains enabled for admin-created, already-confirmed synthetic users. Setup and run verify this configuration before using API keys. No fixture confirmation emails are sent.

Add `organizationId`, `region`, `vercelProjectId`, `deploymentId`, exact reviewed `commitSha`, one immutable `appOrigins` entry, and the verified `databaseHosts` to the provisioned manifest. Deploy the protected preview before setup; signed application readiness becomes available after schema setup. The one-run manifest is admitted only by the protected main workflow, matches its SHA, and uses the same target guard as fixture creation/cleanup. No permanent target registration is needed.

Setup reads live `information_schema` before writes and requires no Auth users, no application objects and no migration history. It selects the registered PRIMARY session pool on port 5432, verifies TLS, and resets only the temporary project's database password through the [documented password API](https://supabase.com/docs/reference/api/v1-update-database-password). It then applies the existing clean baseline and 001–023 in one transaction, together with canonical version rows (`000`, `001` through `023`). The migration ledger shape was inspected in the live catalog; an incompatible existing ledger is rejected. No production migration history or warehouse rows are copied. A real synthetic bootstrap fixture permits the reviewed operational cutover; its cutover history is recorded atomically, then the fixture is deleted and empty-domain/least-privilege checks run again. Setup is fresh-only: a completed or partially dirty target is not silently overwritten.

Run changes no schema. It obtains a short-lived GitHub OIDC token only from the fixed GitHub Actions endpoint, validates repository/main/SHA/audience/expiry claims, and sends it only to the registered protected Vercel origin. The child receives only its target credentials and public identities, without the Management token or GitHub request token. Fixed stage markers and allowlisted HTTP/SQLSTATE categories support diagnosis; raw provider/child errors, SQL, connection strings and keys are suppressed.

Every attempted temporary password reset is followed by a new random discard password in `finally`, including ambiguous initial-reset timeouts. `run` then deletes the verified temporary Supabase project in `finally`, including failed workloads, and polls until its absence is confirmed. The separate cleanup operation is an idempotent recovery path and permits disposal after the four-hour test expiry, up to 24 hours after creation, while retaining exact live ID/name/organization/region/creation checks and protected-reference denial. A forcibly killed workflow still requires explicit cleanup. The operator separately deletes the temporary Vercel project and confirms provider resource removal; no standing staging database remains.

Run the guards with `node --test tests/staging-load.test.mjs tests/staging-hosted-load.test.mjs tests/hosted-load-bootstrap.test.mjs tests/hosted-load-lifecycle.test.mjs`. These checks verify fail-closed admission, rollback boundaries, malformed-response redaction, password disposal, OAuth/signup quarantine, duplicate prevention, and confirmed deletion. They do not replace the actual authorized hosted rehearsal.

## Interpretation and remaining work

CI results measure a bounded synthetic application/transaction baseline on a shared runner. Hosted results add actual Vercel/Supabase network, Auth and transaction behavior for the recorded target and small synthetic dataset. They do not establish Vercel/Supabase production capacity, a maximum supported league count, actual production RPO/RTO, restored Storage object bytes, payment readiness, or paid AI throughput. Higher-volume capacity conclusions require representative privacy-safe data volumes and a separately reviewed workload. The restore report states its own limitations explicitly.

The lean Node runner uses existing `pg` and Supabase dependencies with native fetch cancellation and timing. Its constant-concurrency, paced workload and threshold checks follow the concepts in [k6 constant VUs](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-vus/) and [k6 thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/), while reusing the application's Auth and database fixtures instead of adding another test runtime.
